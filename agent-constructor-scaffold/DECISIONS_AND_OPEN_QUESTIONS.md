# Decisions and Resolved Open Questions

Status: **resolved for Task 0 approval (including Specialized Agent Harness, Hardware-Gated Local Models, On-The-Fly Subworker HITL, Multi-Stage Formal Verification, & Strict Anti-Mocking Policy)**.

## 1. Core architectural principles (preserved & extended)

1. **AMCA as a Specialized Agent Harness**: AMCA is model-agnostic. Its Primary Agent brain can be powered by any Cloud AI provider (`Gemini`, `xAI`, `OpenAI`, `Anthropic`, or `Custom OpenAI-Compatible`), a **Hardware-Verified Local Model** downloaded to the laptop, or a deterministic offline synthesizer, configured via a **Preliminary Setup Interface** and hot-swappable at any time.
2. **Hardware-Gated Local Model Downloads (`hardware.py`)**: Before any local AI model can be downloaded to the user's laptop, AMCA performs a real OS hardware inspection (total/available RAM, free disk space, CPU cores, GPU/VRAM). If the laptop meets the model's requirements, download is allowed upon user confirmation; if not, the download is strictly refused (`REFUSED_INSUFFICIENT_HARDWARE`).
3. **Independent Subworkers with On-The-Fly HITL & Separate API Keys (`harness.py`)**: Whenever AMCA proposes spawning a Subworker, an **On-The-Fly Human-in-the-Loop (HITL) Interface** prompts the user to approve the Subworker and supply a **separate model and API key** dedicated to that Subworker (which can differ from AMCA's Primary Agent API key).
4. **Zero-Mock Real Implementation**: All AMCA and `amca_agent` modules implement genuine OS hardware inspection, genuine provider/harness routing, genuine symbolic proof evaluation, genuine `ast.parse()` code inspection, genuine file generation, and genuine test execution—never mocks, stubs, or hardcoded fake returns.
5. **Multi-Stage Formal Verification**: Formal verification runs at **3 points**: (Stage 1) every YAML revision for topological, confluence, Hoare pre/postcondition, and security proofs; (Stage 2) across revisions (`rev-N` $\to$ `rev-(N+1)`) for invariant preservation; and (Stage 3) post-construction on the generated Python AST for graph isomorphism ($G_{\text{code}} \cong G_{\text{yaml}}$) and runtime contract guards.
6. **Triple Secret Hygiene**: Primary Agent API keys and Subworker API keys exist only in volatile session memory (`SessionCredentialVault`); target machine external services in YAML use uppercase `secretRef` environment-variable names only.

| **D-09** | **How is persistence handled for sessions, YAML revisions, approvals, proofs, and logs?** | Persist locally as structured JSON/YAML files under `artifacts/agent_sessions/<session_id>/` and `artifacts/constructed_projects/<id>-rev<NNN>/`. API keys (both Primary and Subworker) are never persisted. | Requires zero database dependencies, stays inspectable for researchers, and packages cleanly into the handover ZIP. |
| **D-10** | **How does the repository handle checkpoints without `.git` metadata?** | Because the workspace is not a Git repository, recovery checkpoints use immutable versioned files (`spec-vNNN.yaml`), SHA-256 digests in approval/proof records, and append-only `construction-log.jsonl` entries rather than Git commits. | Aligns with the audit finding that `.git` metadata is absent in `d:\AMCA_Waterfall_Scaffold_v0.2`. |
| **D-11** | **Which actions require explicit user approval?** | (1) **Preliminary Model/Download Setup**: Confirming local model download after passing `hardware.py` inspection. (2) **Approval A (`spec_approval`)**: Locking a structurally `verified` and formally `PROVED` YAML revision. (3) **On-The-Fly Subworker HITL Approval (`subworker_hitl_approval`)**: Approving a proposed Subworker and supplying its independent model/API key. (4) **Approval B (`construction_approval`)**: Generating project files in `artifacts/constructed_projects/`. (5) **Runtime Approval (`run_approval`)**: Executing a machine with runtime inputs. | Ensures every state transition, local model download, subworker creation, and execution is explicitly authorized by the user. |
| **D-12** | **Is cloud/remote deployment in scope?** | **Out of scope** for this release. Output is a local runnable project and a reproducible handover ZIP archive. | Keeps the attack surface minimal and aligns with `VISION_AND_SCOPE.md`. |
| **D-13** | **Which DAG format is delivered?** | Deliver Graphviz DOT source (`machine-dag.dot`) in every constructed project and handover ZIP, render it interactively in Streamlit via `st.graphviz_chart`, and optionally render `.svg`/`.png` if the Graphviz `dot` binary is present on PATH. | Works reliably across hosts even when the system Graphviz binary is not installed on PATH. |
| **D-14** | **How is Formal Verification implemented without heavy external theorem-prover dependencies, and where does it run?** | Implement a pure-Python symbolic predicate & graph-theoretic proof engine in `src/amca_agent/formal_verifier.py` running at **3 stages**: (Stage 1) every YAML revision; (Stage 2) revision-to-revision invariant preservation; and (Stage 3) post-construction AST graph isomorphism ($G_{\text{code}} \cong G_{\text{yaml}}$) and runtime contract guard verification. | Directly serves researchers exploring AMCA White Paper Sections 6.2–6.4 and Experiment E5 while remaining 100% deterministic, fast, and dependency-free. |
| **D-15** | **How do we prevent AI agents from completing tasks with mocks, stubs, or hardcoded fake logic?** | Enforce the **Strict Anti-Mocking Mandate (`AC-18`)**: zero mocks/stubs in `src/` or `app.py`, zero mocking of internal services in `tests/`, and mandatory mutation tests. | Guarantees that every component, hardware check, subworker harness, proof certificate, constructed project, and ZIP archive is genuinely realized. |
| **D-16** | **How does AMCA inspect laptop specs and enforce the local model download gate?** | `src/amca_agent/hardware.py` queries real OS RAM (via `ctypes.windll.kernel32.GlobalMemoryStatusEx` on Windows and `/proc/meminfo` on POSIX), free disk bytes (`shutil.disk_usage`), CPU cores (`os.cpu_count()`), and GPU/VRAM. It compares these metrics against the requested model's `min_ram_available_mb` and `min_disk_free_mb`. If the laptop does not meet the thresholds, it returns `REFUSED_INSUFFICIENT_HARDWARE` and blocks the download. | Prevents out-of-memory crashes or disk exhaustion on user laptops while supporting local AI models when hardware permits. |
| **D-17** | **Can a Subworker use a different AI model and a different API Key from the Primary AMCA Agent, configured on the fly?** | **Yes (`AC-21`).** When AMCA proposes a Subworker, an **On-The-Fly HITL Interface** pauses execution, presents the Subworker's role and rationale, and prompts the user to approve the Subworker and input its own provider, model, and API key (stored under a separate role key in `SessionCredentialVault`). If declined, AMCA falls back to the Primary Agent. | Gives the user complete Human-in-the-Loop control and credential isolation across multi-vendor agent hierarchies. |
| **D-18** | **Where does the user configure the Primary Agent's API Key or Local Model before starting?** | Both `app.py` (GUI) and `amca_agent.cli` (CLI) present a **Preliminary Harness Setup & Combo Configuration Interface (`AC-19`, `AC-22`)** at startup (and accessible anytime for hot-swapping) before or alongside the opening machine-construction prompt. | Provides a clear, dedicated onboarding flow for model selection, API key entry, 9Router/Ollama/LM Studio/OpenCode discovery, Combo fallback setup, and laptop hardware inspection. |
| **D-19** | **How does AMCA integrate with 9Router, Ollama, LM Studio, and OpenCode, and how does it handle Token-Limit / Quota Fallbacks?** | (1) `provider.py` includes dedicated connectors for **9Router** (`http://127.0.0.1:20128/v1`, discovering both individual models and 9Router Combo aliases), **Ollama** (`http://127.0.0.1:11434`), **LM Studio** (`http://127.0.0.1:1234/v1`), and **OpenCode** (`http://127.0.0.1:4096` / CLI). (2) `harness.py` implements **AMCA's Native Combo & Token-Limit Fallback Chain Protocol (`FallbackComboRouter`)** with a 9Router-style Combo Builder UI (`Tier 1 -> Tier 2 -> Tier N`). When any tier hits `context_length_exceeded`, `finish_reason == "length"` truncation, TPM/TPD token limits, or `HTTP 429` quota exhaustion, AMCA compacts the prompt context, logs a sanitized `FallbackTransitionEvent`, and automatically fails over to the next tier in the chain. | Ensures uninterrupted research workflows even when individual cloud or local models hit context window limits, token quotas, or rate limits. |
