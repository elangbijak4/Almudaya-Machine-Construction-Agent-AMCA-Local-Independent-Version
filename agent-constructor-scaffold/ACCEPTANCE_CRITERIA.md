# Acceptance Criteria and Quantitative Thresholds

Status: **reconciled criteria and pre-agreed quantitative bounds (including Specialized Agent Harness, Hardware-Gated Local Models, On-The-Fly Subworker HITL, Multi-Stage Formal Verification, & Anti-Mocking Mandate)**. These criteria (`AC-01`–`AC-21`) extend—and do not replace—the baseline `FR-01`–`FR-10`, `NFR-01`–`NFR-08`, and `CR-UI-01`–`CR-UI-09` requirements.

## 1. Functional, harness, formal verification, anti-mocking, and safety acceptance criteria

| ID | Criterion | Planned Verification & Evidence |
| --- | --- | --- |
| **AC-01** | Both GUI (`app.py`) and CLI (`amca_agent.cli`) greet the user with *“Mesin/agent apakah yang Anda ingin buat?”* (after or alongside the Preliminary Harness Setup) and accept a natural-language request. | Streamlit `AppTest` and CLI integration transcript (`test_conversation_and_spec_approval.py`). |
| **AC-02** | Out-of-scope requests (unrelated to building a machine/agent) are classified as `out_of_scope`, receive a clear scope boundary message, and never trigger YAML drafting or construction. | Unit and integration classification tests (`test_intent_and_approvals.py`). |
| **AC-03** | A supported request produces a parseable `apiVersion: amca/v1alpha1` (`kind: MachineSystem`) YAML that conforms to the schema and explicitly populates `assumptions`, `limitations`, and `unresolvedQuestions` as structured fields (not YAML comments). | Schema unit tests (`test_system_spec.py`) and saved sample specifications. |
| **AC-04** | User can revise the draft in the same session; when a draft is structurally `rejected` or formally `REFUTED`, structural reasons and formal counterexamples are automatically included in the revision prompt context. Prior revisions remain immutable, and approved revisions cannot be overwritten. | Provider revision context test and session immutability test (`test_conversation_and_spec_approval.py`). |
| **AC-05** | Invalid structure, duplicate IDs, missing connections, incompatible ports, cycles, unknown components, and disallowed security policies (`networkPolicy != "deny-by-default"`, `operatingSystemCommands != "deny"`, `secretPolicy != "references-only"`) fail closed. | Negative and adversarial unit tests (`test_system_spec.py` + `test_verifier.py`). |
| **AC-06** | **Two-Stage Approval Gate with Formal Proof Binding**: **Approval A (`spec_approval`)** requires both structural `verified` and Stage 1 Formal Verification `PROVED`, locking `revision`, `specification_sha256`, and `certificate_sha256`. **Approval B (`construction_approval`)** binds to `spec_approval` and authorizes the SDLC, worker plan, and destination path. Construction refuses to run if either approval is missing or if digests mismatch. | Approval tamper and gate enforcement tests (`test_intent_and_approvals.py`, `test_builder_scaffold.py`). |
| **AC-07** | `amca/v1alpha1` YAML and construction plans record `builderEnvironment` (captured runtime OS/Python) and `targetEnvironment` separately, including explicit `unspecified` values where applicable. | Planner unit test and generated manifest inspection. |
| **AC-08** | External service declarations use uppercase environment variable references (`secretRef` matching `^[A-Z][A-Z0-9_]{1,63}$`). Both Primary Agent API keys and Subworker API keys stay in memory only. Automated secret scans across YAML, logs, session files, proof certificates, and handover ZIPs find zero secret values. | Secret-redaction and ZIP security tests (`test_construction_and_zip.py`). |
| **AC-09** | Worker planner defaults to single-agent execution (`policy: minimize-cost`, `useSubagents: false`) and records explicit cost, coordination, and schedule rationale whenever subworkers are proposed. | Planner policy unit tests (`test_intent_and_approvals.py`). |
| **AC-10** | Generated project scaffold matches the approved `amca/v1alpha1` spec and Waterfall SDLC, embeds runtime pre/postcondition guards corresponding to $\{P_c\}\;c\;\{Q_c\}$, and confines all generated file paths inside `artifacts/constructed_projects/<machine_id>-rev<NNN>/`. | Path-safety and manifest verification tests (`test_builder_scaffold.py`). |
| **AC-11** | Every construction step appends a secret-redacted entry to `construction-log.jsonl` (recording timestamp, task ID, `specification_sha256`, action, result, and evidence pointer) and supports checkpoint status inspection/recovery. | Audit log and recovery test (`test_construction_and_zip.py`). |
| **AC-12** | Project verification runs **Stage 3 Formal Refinement Verification** (`G_code ≅ G_yaml` AST isomorphism + contract guard check) alongside actual checks (`compileall`, DAG verification, and executing the generated project's `unittest` suite), recording `passed`/`PROVED`, `failed`/`REFUTED`, or `inconclusive`. | Integration test running Stage 3 formal verifier and generated project tests (`test_construction_and_zip.py`). |
| **AC-13** | For a valid approved `MachineSystem`, construction produces a runnable Python project that executes the reference input (`characters=20; words=4`) and exports a valid DAG `.dot` artifact; invalid, unapproved, or formally `REFUTED` specs produce zero constructed project files. | End-to-end constructor test (`test_construction_and_zip.py`). |
| **AC-14** | Handover ZIP (`<machine_id>-rev<NNN>-handover.zip`) contains generated source, final `machine.yaml`, `formal-proof-certificate.json`, approval records, `README.md`, `machine-dag.dot`, verification report, and redacted logs, while excluding secrets, `.venv*`, `__pycache__`, and unrelated files. | Archive manifest inspection test (`test_construction_and_zip.py`). |
| **AC-15** | Backward compatibility: all 69 baseline `P0`–`P6` tests, all `CR-001` CLI/GUI tests (77 total), `schema_version: "1.0"` execution, and `tools/validate_workflow.py --phase P0..P6` continue to pass in a clean CPython 3.12+ environment. | Full regression suite execution in Task 7. |
| **AC-16** | Full GUI (`app.py`) and CLI (`amca_agent.cli`) parity across the entire constructor lifecycle: preliminary harness setup, hardware inspection, intake, classification, drafting, revision, formal proof inspection, Approval A, planning, on-the-fly Subworker HITL provisioning, Approval B, construction, verification, and ZIP export. | CLI integration suite and Streamlit `AppTest` suite. |
| **AC-17** | **Multi-Stage Formal Verification (`formal_verifier.py`)**: (1) **Stage 1** algorithmically proves source-to-sink reachability (`FO-TOP-01`), Church-Rosser schedule confluence (`FO-CON-01`), Hoare pre/postcondition entailment $Q_u \vdash P_v$ (`FO-HOA-01`), acceptance goal entailment (`FO-GOAL-01`), and security non-interference (`FO-SEC-01`), and refutes compositional flaws even when port types match; (2) **Stage 2** checks invariant preservation across revisions (`rev-N` $\to$ `rev-(N+1)`); (3) **Stage 3** parses generated Python files with `ast.parse()` to prove graph isomorphism ($G_{\text{code}} \cong G_{\text{yaml}}$) and contract guard presence. | Dedicated unit, AST-mutation, and integration proof tests (`test_formal_verifier.py` + `test_construction_and_zip.py`). |
| **AC-18** | **Zero-Mock Real Implementation & Mutation Verification**: Production modules contain zero mocks, stubs, `TODO`/`pass` placeholders, or hardcoded proof/build returns. Automated tests do not mock internal AMCA/`amca_agent` services and include non-reference topologies and AST-mutation tests. | AST scan of `src/` + mutation tests in `test_formal_verifier.py` and `test_construction_and_zip.py`. |
| **AC-19** | **Preliminary Harness Setup, 9Router/Ollama/LM Studio/OpenCode Connectors, & Hot-Swapping**: GUI and CLI provide a preliminary setup interface where users can configure and hot-swap AMCA's Primary Agent across Cloud APIs (`Gemini`, `xAI (Grok)`, `OpenAI`, `Anthropic`, `Custom OpenAI-Compatible`), **9Router (`nine_router` individual models & 9Router Combos)**, **Local AI Runtimes (`Ollama`, `LM Studio`, `OpenCode` with live model discovery)**, `Local Model`, `amca_combo`, or `Offline Deterministic` mode without losing session state. | Unit and GUI/CLI integration tests (`test_hardware_and_harness.py`, `test_conversation_and_spec_approval.py`). |
| **AC-20** | **Hardware Inspection Gate for Local Model Downloads (`hardware.py`)**: Before any local model can be downloaded to the laptop (directly or via Ollama/LM Studio pull), AMCA inspects actual host RAM (total & available), free disk space, CPU cores, and GPU/VRAM. If hardware specs meet the model's requirements (`ELIGIBLE`), downloading/binding is permitted upon user confirmation; if specs are insufficient, downloading is strictly blocked (`REFUSED_INSUFFICIENT_HARDWARE`) with a detailed deficit report. | Real OS hardware query tests and high/low threshold eligibility tests (`test_hardware_and_harness.py`). |
| **AC-21** | **On-The-Fly HITL Subworker Approval & Independent API Key / Combo Provisioning**: When AMCA proposes spawning a Subworker, an on-the-fly Human-in-the-Loop (HITL) interface appears in GUI and CLI requiring explicit user approval and allowing the user to input a **separate model, API key, 9Router Combo, or AMCA Combo chain** for that Subworker (distinct from the Primary Agent's key). Declining the Subworker cleanly falls back to the Primary Agent. | Subworker HITL lifecycle, multi-key isolation, and fallback tests (`test_hardware_and_harness.py`, `test_builder_scaffold.py`). |
| **AC-22** | **Native AMCA Combo & Token-Limit Fallback Chain Protocol (`FallbackComboRouter`)**: Users can configure 9Router-style ordered **Combo Fallback Chains (`Tier 1 -> Tier 2 -> Tier 3 ...`)** in GUI and CLI (or bind directly to a 9Router Combo). When an active tier encounters a token limit (`context_length_exceeded`, `finish_reason == "length"` truncation, TPM/TPD limit), rate limit (`HTTP 429`), or quota exhaustion, AMCA automatically compacts context (preserving canonical YAML and formal counterexamples), logs a sanitized `FallbackTransitionEvent`, and seamlessly fails over to the next tier in the chain. | Token-limit, `finish_reason=="length"`, and `HTTP 429` multi-tier failover unit & integration tests (`test_hardware_and_harness.py`). |
| **AC-23** | **Consistency Verification Against the Three User Books (`USER_MANUAL.md`, `USER_GUIDE.md`, `USER_TUTORIAL.md`)**: The finished application must be verified against `help/USER-MANUAL.md` (`USER_MANUAL.md`), `help/USER-GUIDE.md` (`USER_GUIDE.md`), and `help/USER-TUTORIAL.md` (`USER_TUTORIAL.md`) as a mandatory verification oracle (`VO-01`–`VO-06`). The application must satisfy 100% of the minimum capabilities documented in those three books, and if any additional features/commands are added during implementation that remain consistent with that baseline, all three books must be updated to reflect the exact final behavior. | Automated CLI/GUI command & feature parity check against `USER_MANUAL.md`, `USER_GUIDE.md`, and `USER_TUTORIAL.md` in Task 7 (`docs/14-agent-constructor-verification-and-handover.md`). |

## 2. Pre-agreed quantitative limits and safety thresholds

| Parameter | Limit / Threshold | Enforcement Point |
| --- | --- | --- |
| **Max YAML specification size** | `65,536` bytes (64 KiB) | `specification.py` & `system_spec.py` |
| **Max machines / nodes per system** | `1` to `64` machines | `schema.py` & `system_spec.py` |
| **Max connections / edges per system** | `0` to `128` connections | `schema.py` & `system_spec.py` |
| **Max per-machine config size** | `16,384` canonical JSON bytes (16 KiB) | `schema.py` & `system_spec.py` |
| **Max user prompt / chat turn length** | `8,000` characters per turn; max `8` recent turns in provider context | `provider.py` & `intent.py` |
| **LLM provider HTTP timeout & max response** | `45` seconds timeout; `1,000,000` bytes (1 MB) max response payload; `0` automatic unapproved retries | `provider.py` & `harness.py` |
| **Local model hardware safety margin** | Available RAM $\ge$ model `min_ram_available_mb`; Free Disk $\ge$ model `min_disk_free_mb` ($\ge 1.5\times$ download size) | `hardware.py` (`evaluate_local_model_eligibility`) |
| **Allowed construction destination root** | Strictly inside `artifacts/constructed_projects/<machine_id>-rev<NNN>/` | `builder.py` (`Path.resolve()` check) |
| **Max generated files per constructed project** | `64` files; max `1,048,576` bytes (1 MiB) per generated file | `builder.py` & `packager.py` |
| **Max handover ZIP archive size** | `10,485,760` bytes (10 MiB) | `packager.py` |
